GRAMÁTICA BNF - JERCompiler
===========================

Esta referencia describe la gramática formal y el esquema sintáctico del lenguaje
general JER implementado en analizador/JERCompiler_JJTree.jjt (JJTree; genera el
AST que usará la fase de análisis semántico). La gramática JavaCC original sin
JJTree, analizador/JERCompiler.jj, ya no se usa.

PROGRAMA
--------

<Programa> ::= ( <DeclaracionGlobal> | <DeclaracionFuncion> )* EOF

<DeclaracionGlobal> ::= ( <DeclaracionVariable> | <DeclaracionConstante> ) ';'

DECLARACIONES Y ARREGLOS
------------------------

<DeclaracionVariable>  ::= <TipoDato> IDENTIFICADOR <Dimensiones> ( '->' <Condicion> )?
<DeclaracionConstante> ::= 'CONST' <TipoDato> IDENTIFICADOR <Dimensiones> '->' <Condicion>
<Dimensiones>          ::= ( '[' <Expresion> ']' )*

<TipoDato> ::= 'ENT' | 'DEC' | 'CAD' | 'CAR' | 'BOO'

El inicializador de una variable normal es opcional (una CONST siempre lo exige):
  ENT contador;                      # sin inicializar
  ENT edades[3] -> [18, 20, 21];
  DEC notas[2][2] -> [[9.5, 8.0], [7.0, 10.0]];

El valor de inicialización es <Condicion>, no solo <Expresion>: una comparación
(o una combinación con AND/OR/NOT) también es un valor válido, no solo para
variables BOO — ver la sección CONDICIONES COMO VALOR más abajo.

FUNCIONES Y SENTENCIAS
----------------------

<DeclaracionFuncion> ::= 'FUN' <TipoRetorno> IDENTIFICADOR '(' <ListaParametros>? ')' <Bloque>
<TipoRetorno>         ::= <TipoDato> | 'VACIO'
<ListaParametros>     ::= <Parametro> ( ',' <Parametro> )*
<Parametro>           ::= <TipoDato> IDENTIFICADOR
<Bloque>              ::= '{' <Sentencia>* '}'

FUN exige declarar su tipo de retorno antes del nombre. 'VACIO' es exclusivo de
<TipoRetorno> (no es un <TipoDato> válido para variables, constantes ni
parámetros): marca una función que no retorna valor y por lo tanto no puede
usarse dentro de una expresión, solo llamarse por su efecto.
  FUN ENT sumar(ENT a, ENT b) { RET a + b; }
  FUN VACIO principal() { IMP "hola"; }

<Sentencia> ::= <DeclaracionVariable> ';'
              | <DeclaracionConstante> ';'
              | <AsignacionOLlamada>
              | <EstructuraSi>
              | <EstructuraMientras>
              | <EstructuraRepetir>
              | <EstructuraEvaluar>
              | <EstructuraHacer>
              | 'IMP' <Expresion> ';'
              | 'OBT' IDENTIFICADOR ';'
              | 'RET' <Condicion> ';'
              | 'TERMINAR' ';'

<AsignacionOLlamada> ::= IDENTIFICADOR '(' <Argumentos>? ')' ';'
                       | IDENTIFICADOR ( '++' | '--' ) ';'
                       | IDENTIFICADOR <Acceso>+ ( ( '++' | '--' ) ';' | <OperadorAsignacion> <Condicion> ';' )
                       | IDENTIFICADOR <OperadorAsignacion> <Condicion> ';'

<OperadorAsignacion> ::= '->' | '+->' | '-->'
<Acceso>             ::= '[' <Expresion> ']'
<Argumentos>         ::= <Expresion> ( ',' <Expresion> )*

'RET' y el lado derecho de una asignación ('->', '+->', '-->') también aceptan
<Condicion> en vez de solo <Expresion> — ver CONDICIONES COMO VALOR.

CONTROL DE FLUJO
----------------

<EstructuraSi> ::= 'SI' <Condicion> <Bloque> ( 'SINO' ( <EstructuraSi> | <Bloque> ) )?

  El operador 'SINO' se puede encadenar directamente con otro 'SI' (else-if) sin
  necesitar llaves adicionales alrededor del SI anidado:
    SI nota > 90 {
        IMP "excelente";
    } SINO SI nota > 70 {
        IMP "bien";
    } SINO {
        IMP "revisar";
    }

<EstructuraMientras> ::= 'MIENTRAS' <Condicion> <Bloque>

<EstructuraRepetir> ::= 'REPETIR' '(' <DeclaracionVariable> ';' <Condicion> ';' <PasoRepetir> ')' <Bloque>
<PasoRepetir>        ::= IDENTIFICADOR ( ( '+->' | '-->' ) <Expresion> | '++' | '--' )

  Ciclo estilo 'for' clásico: declara su propia variable de control, condición de
  parada y paso de incremento/decremento, todo dentro de la cabecera entre
  paréntesis (reemplaza la forma antigua 'REPETIR N { ... }'):
    REPETIR (ENT i -> 0; i < 10; i++) {
        IMP i;
    }

<EstructuraHacer> ::= 'HACER' <Bloque> 'MIENTRAS' '(' <Condicion> ')' ';'

  Ciclo que se ejecuta al menos una vez (do-while); la condición al final va
  entre paréntesis obligatorios, y la sentencia completa termina con ';':
    HACER {
        IMP i;
        i--;
    } MIENTRAS (i > 0);

<EstructuraEvaluar> ::= 'EVALUAR' <Expresion> '{'
                         ( 'CUANDO' <Expresion> ':' <Sentencia>* )+
                         ( 'PRED' ':' <Sentencia>* )? '}'

CONDICIONES COMO VALOR
-----------------------

<Condicion>           ::= <ExpresionLogica>
<ExpresionLogica>     ::= <ExpresionRelacional> ( ( 'AND' | 'OR' ) <ExpresionRelacional> )*
<ExpresionRelacional> ::= ( 'NOT' )? <Expresion> ( <OperadorRelacional> <Expresion> )?
<OperadorRelacional>  ::= '=' | '!=' | '>' | '<' | '>=' | '<='

<Condicion> es un superconjunto estricto de <Expresion>: cualquier cosa que
<Expresion> puede matchear, <Condicion> también (vía la rama sin comparador de
<ExpresionRelacional>). Esto habilita dos cosas, deliberadamente simétricas:

1. Una condición (comparación, o combinación con AND/OR/NOT) es un valor válido
   donde antes solo se aceptaba <Expresion>: inicializador de variable/constante,
   'RET', y el lado derecho de una asignación. Antes, una variable/función BOO
   solo podía inicializarse/retornarse/reasignarse con VERDADERO/FALSO u otra
   variable BOO — nunca con el resultado vivo de una comparación:
     BOO mayor -> a > b;
     FUN BOO esPositivo(ENT n) { RET n > 0; }

2. Una expresión sola (sin comparador), como una variable BOO, también es una
   condición válida por sí misma en SI/MIENTRAS/REPETIR/HACER...MIENTRAS — no
   hace falta comparar explícitamente:
     SI bandera { ... }
     MIENTRAS NOT activo { ... }

Nota de diseño para la fase semántica (aún no implementada): la condición de
SI/MIENTRAS/REPETIR/HACER debe exigirse de tipo BOO estrictamente — NO se van a
adoptar semánticas "truthy" (tratar ENT/DEC no-cero como verdadero, al estilo
C). Sintácticamente cualquier <Expresion> ya es aceptada como condición (ver
arriba); ese chequeo de tipo queda pendiente, a cargo del analizador semántico.

Los paréntesis para agrupar (tanto aritmética como condiciones) se resuelven en
<Base>, no aquí — ver EXPRESIONES Y OPERACIONES: <ExpresionRelacional> no tiene
su propia rama de paréntesis porque, al no vivir dentro de la cadena aritmética
normal, no puede "seguir" encadenando operadores después de cerrar un grupo
(p. ej. "(a + b) * 2 / c" como valor de un RET rompía si el paréntesis se
resolvía a este nivel).

EXPRESIONES Y OPERACIONES
-------------------------

<Expresion>      ::= <Termino> ( ( '+' | '-' ) <Termino> )*
<Termino>        ::= <Factor> ( ( '*' | '/' | '%' ) <Factor> )*
<Factor>         ::= <Base> ( ( '**' | '//' ) <Base> )*
<Base>           ::= '-' <Base>
                   | IDENTIFICADOR '(' <Argumentos>? ')'
                   | '(' <Condicion> ')'
                   | <LiteralArreglo>
                   | <Valor>

<LiteralArreglo> ::= '[' ( <Expresion> ( ',' <Expresion> )* )? ']'
<Valor>          ::= NUMERO_ENTERO | NUMERO_DECIMAL | CADENA | CARACTER
                   | 'VERDADERO' | 'FALSO' | IDENTIFICADOR <Acceso>*

'(' en <Base> acepta <Condicion> (no solo <Expresion>): cubre tanto un
paréntesis puramente aritmético de agrupación ("(a + b) * 2") como una
condición agrupada ("(a > b) AND c"), sin ambigüedad, porque <Condicion> es
superconjunto estricto de <Expresion> (ver CONDICIONES COMO VALOR).

LÉXICO Y COMENTARIOS
--------------------

- Comentarios de línea: Comienzan con '#' hasta el final de la línea.
- Comentarios de bloque: Inician con '/**' y finalizan con '**/'.
- Operadores aritméticos: '+' (suma), '-' (resta/unario), '*' (mult), '/' (div),
  '%' (módulo), '**' (potencia), '//' (raíz cuadrada).
- Asignaciones: '->' (asignación), '+->' (suma y asigna), '-->' (resta y asigna).
- Incremento/decremento: '++', '--' (como sentencia propia o como paso de REPETIR).
- Comparación de igualdad: '=' (se usa un solo signo igual para comparar).

ESTRATEGIA DE RECUPERACIÓN DE ERRORES (MODO PÁNICO)
---------------------------------------------------

Principio general: cada regla de recuperación usa contexto que la propia gramática
ya conoce en ese punto (qué construcción se está parseando, si una llave/paréntesis
alcanzó a abrirse, si el bloque puede ser legítimamente seguido por SINO, etc.) en
vez de adivinar el significado de un token después de que la excepción ya ocurrió.
El diagnóstico por excepción genérica (capas de heurísticas sobre el token que causó
el fallo) se reserva como último recurso, y solo dispara si se corrobora contra lo
que la gramática esperaba en ese punto (nunca por la sola identidad del token).

1. Cabeceras entre paréntesis: la lista de parámetros de una función y la cabecera
   de REPETIR '(declaración; condición; paso)' comparten la misma recuperación
   (recuperarCabeceraParentizada): si el paréntesis de apertura ya se consumió,
   salta hasta su ')' de cierre respetando paréntesis anidados dentro de la
   expresión; si nunca se abrió, salta directo hasta '{' sin necesitar un ')' que
   quizás no exista. Evita que un parámetro o un paso rotos se reinterpreten como
   una declaración global o una sentencia nueva.

2. Sincronización por FIRST(Sentencia) refinada: el recuperador se detiene al
   detectar el inicio de la siguiente sentencia (ENT, DEC, SI, IMP, etc.). Un
   IDENTIFICADOR sólo cuenta como inicio si le sigue un operador de asignación
   ('->', '+->', '-->'), '(', '[', '++' o '--'; de lo contrario se trataría
   cualquier identificador suelto como sincronización y se reanalizaría basura,
   generando errores en cascada.

3. Resiliencia de bloques: si falta la llave '{' de un Bloque, el error se
   reporta y se analizan TODAS las sentencias del cuerpo huérfano (no sólo la
   primera), hasta encontrar '}', SINO, FUN o EOF. El recuperador recuerda el
   token de apertura realmente consumido (no solo un booleano): si el bloque
   nunca abrió, la '}' que encuentra normalmente pertenece al bloque exterior y
   se deja sin consumir — salvo que sea el cuerpo de una función (nada por
   encima la reclamaría jamás) o que lo siguiente sea otra '}'/SINO/CUANDO/PRED
   (señal de que esa '}' compensa la apertura fantasma de este mismo bloque).
   El cuerpo "then" de un SI se marca como "puede terminar en SINO": si le
   falta su '}', el SINO que sigue no se trata como basura, permitiendo que
   una cadena 'SINO SI' recupere el resto de la cadena limpiamente.

4. Protección de llaves durante la sincronización global o de sentencia: si al
   descartar tokens se encuentra una '{' suelta, no se salta token por token
   (eso desbalancearía las llaves); en su lugar se analiza como un Bloque()
   completo, y sus propios errores internos se reportan por separado.

5. Rendición conservadora ante desbalance real de llaves: al entrar a cada
   función se cuenta, de antemano y con certeza (usando la tabla completa de
   tokens), si sus '{' y '}' cuadran. Cuando un bloque interno abrió bien pero
   la sentencia que falló está a punto de "dejar" una '}' ambigua para el
   nivel exterior, y ya se sabe que esa función tiene un desbalance real, no
   hay forma fiable de saber a cuál bloque específico le falta su cierre — es
   una ambigüedad genuina del texto, no una limitación de la heurística. En
   ese caso el analizador se rinde con un único diagnóstico ("la cantidad de
   '{' y '}' en esta función no cuadra") y salta directo a la siguiente FUN,
   en vez de seguir adivinando sentencia por sentencia y atribuir varios
   errores al lugar equivocado.

6. Un FUN anidado (mal ubicado dentro de un bloque) se tolera UNA vez como
   sentencia inválida; su recuperación (recuperarFunAnidado) descarta la
   cabecera completa de esa "otra función" (tipo de retorno, nombre,
   parámetros) y, si llega a abrir, también su cuerpo entero — a diferencia
   de la sincronización normal de sentencia, NO se detiene en un tipo de dato
   o identificador que luzca como inicio de sentencia, porque eso es
   precisamente la cabecera de la función anidada, no una sentencia suelta
   del bloque actual (detenerse ahí generaba una cascada de 2-4 errores
   espurios por cada función que quedaba así de anidada). Un SEGUNDO FUN
   inmediato ya no se tolera: es señal de que este bloque nunca va a
   encontrar su '}' real, y se deja que '}' falle con el único diagnóstico
   del punto 5.

7. Un identificador seguido de otro identificador (p. ej. tras un ';' faltante)
   es el único solape real entre "faltan dos valores sin operador entre ellos"
   y "falta ';'/'->' antes de la siguiente sentencia": se desambigua mirando si
   el segundo identificador arranca a su vez una <AsignacionOLlamada> válida
   ('->', '+->', '-->', '(', '++', '--' o '['). Si sí, gana el diagnóstico de
   ';'/'->' faltante (es la sentencia siguiente); si no, gana "falta un
   operador" (es un valor suelto).

8. Supresión de diagnósticos derivados: los mensajes genéricos ("token
   inesperado", coma o cierre fuera de lugar) se suprimen si aparecen a menos
   de dos tokens del último error ya reportado, evitando que un solo error real
   produzca varios diagnósticos redundantes. Los mensajes específicos (tipo de
   estructura, instrucción incompleta, palabra reservada mal escrita, etc.)
   siempre se reportan, sin importar la distancia. Los antiguos chequeos por
   identidad de token (p. ej. "todo RET/SINO/CUANDO/PRED que aparezca aquí está
   mal usado") se eliminaron: esos casos ya se reportan por llamada directa
   desde la gramática en el momento en que se detectan, y un chequeo genérico
   por identidad de token resultaba en falsos positivos cuando el mismo token
   aparecía como víctima colateral de un error distinto.
